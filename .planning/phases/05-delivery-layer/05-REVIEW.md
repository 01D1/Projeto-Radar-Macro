# Phase 05: Code Review Report

**Reviewed:** 2026-05-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

The delivery layer covers Streamlit pages, a Telegram bot, a PDF report generator, and scheduler
integration. The foundational patterns are sound — parameterized SQL, try/finally connection close,
in-memory PDF bytes, and no hardcoded credentials. However, five blocker-level issues were found:
a token-in-URL log leak, an XSS vector in the Streamlit ativo page, a double-execution bug present
in all four page files, a conviction-score filter that is documented but never actually applied, and
a `dividend_yield` format bug that renders a decimal fraction as if it were already a percentage.
Seven warnings cover type safety, incorrect truthiness checks, missing test coverage, and a
`get_connection()` API mismatch in `intelligence_layer.py`.

## Critical Issues

### CR-01: Telegram token exposed in exception log when `requests` itself raises

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/telegram_bot.py:272`

**Issue:** When `requests.post()` raises a network-level exception (e.g., `ConnectionError`,
`Timeout`), the broad `except Exception as exc` clause logs the full exception message at line 272:

```python
log.warning(f"[Telegram] falha (tentativa {attempt}/{retry}): {exc}")
```

The URL passed to `requests.post()` contains the token inline:
`https://api.telegram.org/bot{self.token}/sendMessage`. Several `requests` exception types
(notably `ConnectionError`) embed the full URL in their string representation, meaning
`str(exc)` will contain the token. Constraint T-05-02 explicitly forbids the token from
appearing in logs.

**Fix:** Sanitize the exception message before logging, or log only the exception type:

```python
except Exception as exc:
    # Strip any URL (and therefore token) from the exception message
    safe_msg = type(exc).__name__
    log.warning(f"[Telegram] falha (tentativa {attempt}/{retry}): {safe_msg}")
```

### CR-02: XSS via unescaped LLM-generated content rendered as Markdown in `inteligencia_ativo.py`

**File:** `Analista de Investimentos/scanner_quant_profit_b3/pages/inteligencia_ativo.py:76-79`

**Issue:** The `bull_case` and `bear_case` fields are fetched from the database (originally
generated by the LLM) and rendered directly with `st.markdown()`:

```python
st.markdown(thesis.get("bull_case", "—"))
st.markdown(thesis.get("bear_case", "—"))
```

`st.markdown()` in Streamlit renders arbitrary Markdown including inline HTML unless the content
is explicitly escaped. If a threat actor can influence thesis content (e.g., via a poisoned news
article that causes the LLM to embed `<script>` tags or `[text](javascript:...)` links), this will
render as HTML in users' browsers. The project connects to external LLMs and news sources, making
this a real injection surface.

**Fix:** Use `st.write()` (plain text) or escape the content before display:

```python
import html
st.write(thesis.get("bull_case", "—"))          # safe: no HTML rendering
st.write(thesis.get("bear_case", "—"))
```

If Markdown formatting from the LLM is intentional, sanitize with `bleach` or a similar library
before passing to `st.markdown()`.

### CR-03: All four page files execute `main()` twice on every Streamlit page load

**Files:**
- `scanner_quant_profit_b3/pages/inteligencia_watchlist.py:99-101`
- `scanner_quant_profit_b3/pages/inteligencia_ativo.py:137-139`
- `scanner_quant_profit_b3/pages/inteligencia_macro.py:123-125`
- `scanner_quant_profit_b3/pages/inteligencia_oportunidades.py:70-72`

**Issue:** Every page ends with both a `__main__` guard call and an unconditional bare call:

```python
if __name__ == "__main__":
    main()

main()   # <-- always executes, even when loaded by st.navigation()
```

When Streamlit loads a page file via `st.navigation().run()`, it executes the module at the
top level. The bare `main()` on the final line runs unconditionally, and the `if __name__`
block also runs because Streamlit sets `__name__` to `"__main__"` for the active page.
Result: every DB query fires twice, every chart renders twice, and the PDF is generated twice
per page load. This doubles database load and Anthropic API calls that may be triggered
indirectly via `ReportGenerator`.

**Fix:** Remove the bare unconditional call and keep only the guard:

```python
if __name__ == "__main__":
    main()
```

Streamlit's `st.navigation` page runner calls the module-level code directly; the `main()`
function should only be defined, not called at module level.

### CR-04: Conviction-score `>= 40` filter documented but never enforced — IPE_EVENT signals
always bypass threshold

**File:** `Analista de Investimentos/12_PYTHON/src/intelligence_layer.py:506-580`

**Issue:** The docstring for `compute_opportunity_signals()` states:
> "Only signals with conviction_score >= 40 are included."

The code comment at line 578 repeats: "filter >= 40 already applied above." But no such filter
exists anywhere in the function body. All three signal branches use `if score > 0` as their
only guard. `_score_ipe_event()` returns a binary value of exactly `30` when an IPE event is
found — which is below 40. This means:

1. IPE_EVENT signals with score=30 are appended and stored, contradicting the spec.
2. DCF_DIVERGENCE scores range 1–40 (the proportional formula produces `int(min(..., 40))`).
   A score of 1 also bypasses the threshold that is claimed to exist.
3. The comment "filter >= 40 already applied above" is a lie, creating false confidence
   during future maintenance.

**Fix:** Add the missing filter explicitly after the `signals.sort()` call:

```python
signals.sort(key=lambda s: s.conviction_score, reverse=True)
signals = [s for s in signals if s.conviction_score >= 40]
return signals[:3]
```

Also update `_score_ipe_event()` — its binary score of 30 will never pass the threshold, so
either raise the return value to 40+ or document that IPE events intentionally cannot qualify.

### CR-05: `dividend_yield` rendered as percentage with wrong scale in PDF

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/pdf_report.py:278`

**Issue:** `dividend_yield` is stored as a decimal fraction in the database (e.g., `0.048` for
4.8%). The `_valuation_section` method formats it via `_fmt_pct`:

```python
def _fmt_pct(v: object) -> str:
    try:
        return f"{float(v):+.1f}%"
    ...
rows.append(("Dividend Yield", _fmt_pct(multiples.get("dividend_yield"))))
```

`_fmt_pct` renders the raw float with a `%` suffix, so `0.048` is printed as `+0.0%` instead
of `+4.8%`. The fixture data confirms this: `"dividend_yield": 0.048` would display as `+0.0%`.
This is silent data corruption in client-facing financial output.

**Fix:** Multiply by 100 before formatting, or add a dedicated formatter:

```python
def _fmt_yield(v: object) -> str:
    try:
        return f"{float(v) * 100:.2f}%"
    except (TypeError, ValueError):
        return "-"

rows.append(("Dividend Yield", _fmt_yield(multiples.get("dividend_yield"))))
```

## Warnings

### WR-01: `current_price=0.0` silently suppressed in `send_valuation_update()`

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/telegram_bot.py:160`

**Issue:**

```python
if current_price:
    lines.append(f"Preço atual: `R$ {current_price:,.2f}`")
```

The truthiness check `if current_price` evaluates to `False` when `current_price=0.0`. While a
price of zero is economically meaningless, a recently-suspended stock or an asset with a data
error could legitimately produce `0.0`. Silently omitting it is harder to diagnose than showing
"R$ 0.00" or raising. Additionally, the type annotation says `float | None = None`, meaning the
caller can pass `0.0` expecting it to appear.

**Fix:**

```python
if current_price is not None:
    lines.append(f"Preço atual: `R$ {current_price:,.2f}`")
```

### WR-02: `intelligence_layer.run_ticker()` calls `get_connection()` without `DB_PATH` argument

**File:** `Analista de Investimentos/12_PYTHON/src/intelligence_layer.py:653`

**Issue:**

```python
conn = get_connection()
```

All other callers in the codebase (`scheduler.py`, `data.py`) call `get_connection(DB_PATH)`.
The signature of `get_connection` accepts an optional path parameter defaulting to the module-
level `DB_PATH`. If the default is not set or is overridden in tests, `run_ticker()` will silently
connect to the wrong database. The `test_morning_brief_calls_send_daily_brief` test patches
`src.ingestion.db.get_connection` with a lambda that accepts `*a, **k`, masking this divergence
rather than enforcing it.

**Fix:**

```python
from src.ingestion.db import DB_PATH, get_connection
conn = get_connection(DB_PATH)
```

### WR-03: `_post()` retry loop does not `return False` on non-429 HTTP errors — falls through to
retry without the correct delay application

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/telegram_bot.py:248-278`

**Issue:** On a non-429 HTTP error response, the code logs a warning and falls through to the
bottom of the `for` loop. The `if attempt < retry: time.sleep(delay); delay *= 2` block then
fires. But crucially, `continue` is only used for the 429 path. For all other errors the flow
falls through from the HTTP error log at line 260 to the `except` block's implicit exit,
and then proceeds to the backoff. This is fine for exceptions, but for non-exception HTTP errors
the code never re-uses `continue` — instead it falls to the delay at the end of the loop.
The bug: on the last retry attempt (`attempt == retry`), a non-429 HTTP error logs the warning
but does not sleep (correct), yet it also does not immediately `return False`. It allows the loop
to end and hits the `log.error` + `return False` at line 278. This is functionally correct but
the comment "continue" intent for 429 path creates misleading asymmetry. More concretely:
on 4xx errors other than 429, the full `retry` iterations are exhausted even though retrying a
400 Bad Request is pointless.

**Fix:** Add early return for terminal HTTP errors (4xx except 429):

```python
if 400 <= resp.status_code < 500 and resp.status_code != 429:
    log.error(f"[Telegram] erro terminal {resp.status_code} — sem retry")
    return False
```

### WR-04: `get_asset_detail()` calls `get_macro_panel()` inside the `try` block after the
connection is open — if `get_macro_panel()` raises, `conn` from `get_asset_detail` is still
closed by `finally`, but `get_macro_panel` opens and closes its own connection independently.
The nested call inside an active connection is a connection-count risk under SQLite's
default WAL mode.

**File:** `Analista de Investimentos/12_PYTHON/src/dashboard/data.py:107`

**Issue:** `get_asset_detail()` opens `conn`, performs 4 queries, then calls `get_macro_panel()`
at line 107 while `conn` is still open. `get_macro_panel()` opens a second connection to the
same SQLite file and runs 5 queries. SQLite in WAL mode allows multiple readers, but this
pattern doubles the number of open file handles per Streamlit request and will cause a
`database is locked` error if the database is opened in non-WAL (default journal) mode.
The project does not document WAL mode as a deployment requirement.

**Fix:** Call `get_macro_panel()` before opening `conn` (it is independently cached anyway):

```python
@st.cache_data(ttl=300)
def get_asset_detail(ticker: str) -> dict | None:
    macro = get_macro_panel()   # cached call, independent connection
    conn = get_connection(DB_PATH)
    try:
        ...
        result["macro"] = macro
        return result
    finally:
        conn.close()
```

### WR-06: `test_get_opportunities` asserts structure only `if opps:` — test passes vacuously
when fixture data is filtered out by `computed_date` guard

**File:** `Analista de Investimentos/12_PYTHON/tests/test_dashboard_data.py:194-206`

**Issue:** `get_opportunities()` filters with:

```sql
WHERE computed_date = (SELECT MAX(computed_date) FROM opportunity_signals)
```

The fixture inserts `computed_date = "2026-05-18"`. If the test runs on a different date,
`MAX(computed_date)` returns `"2026-05-18"` and the filter matches correctly. However, the
test still uses `if opps:` to guard the structural assertions, meaning that if `opps` is empty
for any reason, all assertions are silently skipped and the test passes green:

```python
if opps:                          # ← test passes vacuously when empty
    assert "ticker" in opps[0]
    assert "conviction_score" in opps[0]
```

Since the fixture unconditionally inserts one signal, `opps` should always be non-empty.
The test should assert this invariant.

**Fix:**

```python
opps = get_opportunities()
assert len(opps) >= 1, "fixture should produce at least one opportunity signal"
assert "ticker" in opps[0]
assert "conviction_score" in opps[0]
```

### WR-07: No test for `send_morning_call_summary()` YAML frontmatter stripping logic

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/telegram_bot.py:112-124`

**Issue:** `send_morning_call_summary()` contains non-trivial string parsing logic to strip YAML
frontmatter:

```python
if content.startswith("---"):
    end = content.find("---", 3)
    if end != -1:
        content = content[end + 3 :].lstrip()
```

The `content.find("---", 3)` search starts at offset 3, which is the character immediately
after the opening `---`. If the first line is exactly `---\n`, offset 3 is `\n`, and the next
`---` is the closing fence. This works correctly. However, there is an edge case: if the
frontmatter itself contains a line that begins with `---` (e.g., a YAML value with leading
dashes), the parser strips too early. No test covers any frontmatter scenario — the test suite
has no test for this function at all. Given this is financial content going to clients,
malformed output is a quality risk.

**Fix:** Add a test that covers: (1) file with frontmatter, (2) file without frontmatter,
(3) file with `---` inside a value field. For production hardening, use a proper YAML
frontmatter parser (e.g., `python-frontmatter` or regex `^---\n.*?\n---\n` with `re.DOTALL`).

### IN-01: `_doc_title` defined as a class variable but overwritten per-instance — Pydantic/FPDF
subclass interaction

**File:** `Analista de Investimentos/12_PYTHON/src/delivery/pdf_report.py:106-107`

**Issue:**

```python
class ReportGenerator(FPDF):
    _doc_title: str = ""
```

`_doc_title` is declared as a class-level attribute. `generate()` then sets
`self._doc_title = f"Relatorio de Investimento - {ticker}"`, which creates an instance attribute
that shadows the class variable correctly. The `generate_from_fixture()` method creates a fresh
instance, so no state leaks between calls. The pattern works but is non-idiomatic — the class
variable serves no purpose since it is always overwritten before `header()` is called.
The cleaner approach is to initialize it in `__init__`.

**Fix:**

```python
def __init__(self, *args, **kwargs):
    super().__init__(*args, **kwargs)
    self._doc_title: str = ""
```

### IN-02: `compute_opportunity_signals()` docstring contradicts code for DCF_DIVERGENCE minimum
score

**File:** `Analista de Investimentos/12_PYTHON/src/intelligence_layer.py:506-508`

**Issue:** The docstring says "conviction_score >= 40 are included" and the comment at line 578
says "filter >= 40 already applied above." But `_score_dcf_divergence()` returns values from
0 to 40, and the `if score > 0` guard passes scores as low as 1. Even after fixing CR-04 to add
the `>= 40` filter, a DCF_DIVERGENCE signal will only be emitted when `score == 40` (i.e., when
divergence >= 100%). The proportional formula maps 20%–100% divergence to 0–40 pts, but the >=40
filter would only pass the top point of that range. The intent may be that DCF_DIVERGENCE should
also have a lower threshold. This inconsistency will cause confusion.

**Fix (documentation):** Clarify in the docstring that DCF_DIVERGENCE signals require >=100%
divergence from current price to pass the threshold, or revise the scoring scale to range 0–100.
